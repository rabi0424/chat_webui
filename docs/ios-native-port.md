# iPhone ネイティブ移植の検討

- 版: v1（検討のみ。実装は未着手）
- 日付: 2026-08-24
- 状態: 提案（採否の判断待ち）

このアプリを iPhone のネイティブアプリへ移す方法を比べる。判断の条件は次の4つ。

| | 条件 |
|---|---|
| ① | iPhone のネイティブ翻訳 API に触れること |
| ② | 追加コストを原則として要しないこと |
| ③ | UI とモーションを高い自由度で決められること |
| ④ | Web 版に機能を足したとき、追従が比較的容易なこと |

利用者は本人のみ。配布・審査・多端末対応は考えなくてよい。

---

## 0. 結論

**薄いネイティブの殻（WKWebView で本番の URL をそのまま開く）＋ 翻訳だけを渡す
ブリッジ**を採る。気に入らない画面が出てきたら、そこだけ後からネイティブへ
差し替える。

理由を一行ずつに畳むと:

- ネイティブを強制しているのは **①だけ**。②③④はどれもネイティブ化を求めていない。
- ②の実体は「作り方」ではなく「署名」で、どの方式でも同じだけかかる。方式の
  選択軸にならない（§3）。
- ③で本当に欲しいもの（触覚・端のスワイプ・システムのシート）は、殻から渡せば
  取れる。全部書き直さないと取れないものは、実はそう多くない。
- ④はネイティブの面積にそのまま比例する。だから**①を満たす最小の面積**が最適解になる。

## 1. まずこのアプリの形を確かめる

移植のしやすさは、アプリの作りで9割決まる。都合のよい点と悪い点が両方ある。

### 都合のよい点

- **生成が Durable Object 側で完結している**。クライアントは途中経過を
  ポーリングして眺めているだけで、接続を保つ責務が無い。ネイティブ側に
  SSE / WebSocket の再接続や、バックグラウンド実行の面倒が一切要らない
  ——閉じても生成は終わるまで走る（要件 §3.3）。ネイティブ化で最も厄介に
  なりがちな部分が、最初から無い。
- **API が `/api/*` に31本、JSON で揃っている**（`app/routes.ts`）。更新は
  PATCH、失敗は `{ error }`——決まりが要件 §4 に書かれていて、ネイティブから
  叩く相手として十分に素直。
- **CSRF ガードがネイティブを閉め出さない**。`app/lib/same-origin.ts` は
  `Sec-Fetch-Site` も `Origin` も無い要求を通す。`URLSession` からの呼び出しは
  そのまま通り、サーバー側の改修が要らない。

### 都合の悪い点

- **画面の重心がクライアントにある**。`app/components` が 7,435行、
  `app/routes/*.tsx` が 2,418行、サーバー専用（`*.server.ts`）を除いた合計で
  16,887行。ネイティブへ書き直すとしたら、ここが丸ごと対象になる。
- **描画の中核に、ネイティブの等価物が無いものが並んでいる**。KaTeX（数式）、
  Mermaid（図）、highlight.js（コード）、自作の remark プラグイン（`remark-alert`
  `remark-sup`）、並べ替えできる表、塊に切って末尾だけ描き直すストリーミング
  （`app/lib/markdown-blocks.ts`）。**これが §5 の結論をほぼ決めている。**
- **端末ごとの設定が localStorage にある**。テーマ・アクセント色・文字サイズ・
  よく使うモデル（`app/lib/recent-models.ts`）・書きかけの下書き。移植先で
  ここがどう扱われるかは、あとで効いてくる（§6.4）。

## 2. ① ネイティブ翻訳 API — 何がネイティブを強制するのか

### Web からは呼べない

Apple の翻訳を JavaScript から呼ぶ API は無い。Safari が持っているのは
「ページ全体を利用者の操作で翻訳する」機能だけで、

- プログラムから起動できない（＝「この応答だけ訳す」ができない）
- ページ全体なので、コードブロックや数式も巻き込む。このアプリは既に入力欄へ
  `translate="no"` を付けてブラウザ翻訳から守っている（要件 §3.3）。同じ理由で
  本文にも掛けたくない

したがって **①はネイティブの実行体を要求する**。ここだけは代替が無い。

### 使えるのは iOS 18 以降の `TranslationSession`

| API | 版 | 何ができるか |
|---|---|---|
| `.translationPresentation(isPresented:text:)` | iOS 17.4+ | システムのシートに訳を出すだけ。**結果を受け取れない** |
| `TranslationSession` | iOS 18+ | 文字列を渡して訳を受け取る。複数まとめて投げられる |

本文に訳を差し込みたいなら後者しかない。押さえておく点:

- 取得は SwiftUI の `.translationTask(_:action:)` 経由に限られる。UIKit
  主体のアプリでも、`UIHostingController` に見えない View を1枚置けば足りる。
- 初回に言語モデルのダウンロード同意が要る（`prepareTranslation()` で先に
  済ませられる）。以後は**オンデバイス・オフライン・無料**。
- 対応の可否は `LanguageAvailability` で確かめる。日本語⇔英語は対応済み。
- アプリが前面にいる間しか動かない。

**要確認（実機で1分）**: PWA の文字選択メニューに「翻訳」が出るか。出るなら
「選んだ範囲だけ訳す」は今日の PWA でも一応できていることになり、①の切迫度が
下がる。ただし戻り値は取れないままなので、本文への差し込みは変わらず不可。

## 3. ② 追加コスト — 実体は「署名」で、方式では変わらない

iPhone に自作アプリを入れるには署名が要る。**これは §4 のどの案でも同額**で、
案の優劣にならない。先に片付けておく。

| | 費用 | 制約 |
|---|---|---|
| Apple Developer Program | $99/年（≒15,000円前後・為替次第） | 制約なし。TestFlight 可 |
| 無料の Personal Team | **0円** | プロファイルが**7日で失効**。App ID 同時10・端末3。TestFlight / Ad Hoc 不可。Push 等の一部 capability 不可 |

有料は月換算で1,200円強。要件 §1.3 の上限（月500円）を超えるので、②に反する。
**無料の Personal Team を採る**。Mac は既に持っている（要件 §1.2）ので追加の
ハードウェアも要らない。

代償は「週に1回 Mac に繋いで ⌘R」。Translation framework は特別な entitlement を
必要としないので、無料枠でも①は満たせる。Push 通知が使えないのは、生成完了を
プッシュで知らせたくなったときに効いてくる（ローカル通知なら無料でも出せるが、
完了時刻が事前に分からないので素直には組めない）。

### ②が効いてくる本当の場所は CI

いま CI は `ubuntu-latest` で型・lint・テストを回している（`.github/workflows`）。
ネイティブのコードを CI に載せるなら macOS ランナーが要る。リポジトリを
private にしたあと（要件 §1.2）macOS ランナーは課金対象になる。

**ネイティブ側を CI に載せなくて済む大きさに保つ**——これが②の実務上の要請で、
そのまま④とも一致する。

## 4. 手法の比較

◎○△✗ は条件をどれだけ満たすか。移植コストは「今から動くまで」、追従コストは
「Web に機能を足すたび毎回」。

| | 案 | ① | ② | ③ | ④ | 移植 | 追従 |
|---|---|---|---|---|---|---|---|
| A | PWA のまま（現状） | ✗ | ◎ | △ | ◎ | 0 | 0 |
| **B** | **薄い殻 + WKWebView(リモート) + ブリッジ** | **○** | **○** | **○** | **◎** | **小** | **ほぼ0** |
| C | B + クロームだけネイティブ | ○ | ○ | ◎ | ○ | 中 | 小 |
| D | Capacitor / Tauri iOS | ○ | ○ | ○ | ○ | 中 | 小〜中 |
| E | フル SwiftUI + `/api/*` | ◎ | ○ | ◎ | ✗ | 特大 | 特大 |
| F | React Native / Expo | ○ | ○ | ○ | ✗ | 特大 | 大 |

### A — PWA のまま

現状。①が満たせないので条件を落とすが、比較の原点として置く。②④は満点で、
③も `env(safe-area-inset-*)` や `@keyframes`、`display: standalone` で
そこそこ行っている。**①を諦められるなら、これが最良である**ことは忘れないでおく。

### B — 薄いネイティブの殻 + WKWebView（推奨）

Xcode で「空のアプリ」を作り、画面いっぱいの `WKWebView` に本番の URL を
読ませる。ネイティブのコードは翻訳ブリッジ込みで**200行前後**に収まる。

- ①: ブリッジで満たす（§5）。
- ②: 署名だけ。ネイティブ側が小さいので CI に載せる必要が無い。
- ③: 中身は Web のまま。ただし WKWebView は Safari と同じエンジンなので、
  CSS のアニメーション・View Transitions・`linear()` イージングはそのまま
  使える。**Web にできないもの（触覚・端のスワイプ戻る・システムのシート）は
  殻から渡せる**。「Web だから自由度が低い」は、殻がある時点でかなり崩れる。
- ④: **デプロイした瞬間にアプリ側も新しくなる**。追従作業がそもそも発生しない。
  ネイティブの capability を使う機能を足したときだけ、殻に数十行足す。
- リスク: 殻が薄いぶん「アプリらしさ」は Web 側の作り込み次第。あとは §6 の
  ログインとデータ保持。

### C — B + クロームだけネイティブ

ナビゲーションバー・サイドバーのドロワー・入力欄をネイティブにし、会話の本文
だけを WebView に残す。③は最も伸びる（キーボード追従、端のスワイプ、
ネイティブのコンテキストメニュー）。

ただし**境界の維持費**を払う。ネイティブの入力欄と Web の本文のあいだで、
下書き・添付・送信中の状態を往復させることになる。いまその状態は `Chat.tsx`
（1,763行）に集中していて、切れ目が入っていない。**B から始めて、不満が
出た画面だけ C にする**のが順当。最初から C を狙う理由が無い。

### D — Capacitor / Tauri iOS

どちらも中身は WKWebView なので、できることは B と変わらない。翻訳のような
OS 固有機能はどのみち自分で Swift のプラグインを書く。得られるのは
「プラグインの作法」だけで、代わりにビルド系がもう一つ増える（②の CI と
④の追従の両方に効く）。Tauri の iOS 対応は署名周りがまだ荒い。

**B に対する上積みが無いので採らない。**

### E — フル SwiftUI + `/api/*`

③①は満点。API はそのまま使えるので、サーバー側（`*.server.ts` 4,627行）は
一切触らずに済む。それでも採らない理由が2つある。

1. **書き直しても Web 依存が残る**。KaTeX の数式と Mermaid の図に、素の
   ネイティブな等価物が無い。ネイティブの Markdown 描画に乗り換えても、
   数式と図のためだけに WKWebView を抱えることになる。**全部書き直した末に、
   いちばん重い依存が残る**。
2. **④が壊れる**。16,887行の表示層と、これから足す機能のすべてが二重になる。
   このリポジトリは「振る舞いを変えたら要件も直す」「テストは壊して確かめる」
   （CLAUDE.md）で品質を保っていて、テストが 9,380行ある。その規律ごと
   二重化するか、片方を規律の外に置くかの二択になる。どちらも悪い。

①のためだけに払う額として、釣り合っていない。

### F — React Native / Expo

`app/lib/*` の純粋な部分は共有できるが、`app/components` は全部書き直し。
そのうえで数式・図・ハイライトは結局 WebView 行きになる。Expo Go では
Translation の native module を積めないので dev build が要る。**E の欠点を
そのまま持ち、E の利点（真にネイティブな描画）を持たない。**

## 5. 推奨案（B）の設計

### 5.1 殻

- `WKWebView` に `https://<本番の Worker>` を読ませるだけ。アセットを
  アプリに同梱しない——同梱すると④が死ぬ（Web を更新するたびに再ビルド）。
- `viewport-fit=cover` は既に入っている（`app/root.tsx`）ので、WebView を
  セーフエリアの下まで広げれば `env(safe-area-inset-*)` がそのまま効く。
- 引っぱって更新（`app/lib/pull-to-refresh.ts`）と WebView の縦バウンスが
  二重にならないよう、`scrollView.bounces = false` を検討する。

### 5.2 ブリッジ — CSP を触らずに済ませる

**`WKScriptMessageHandlerWithReply`（iOS 14+）を使う。** ページ側からは

```js
const results = await window.webkit.messageHandlers.translate.postMessage({
  texts: ["...", "..."], target: "ja",
});
```

と書くだけで Promise が返る。ここが要点で:

- **スクリプトの注入が要らない**。`window.webkit.messageHandlers` はネイティブが
  生やすオブジェクトで、ページの CSP の対象外。`app/lib/csp.ts` にも
  `tests/csp.test.ts` の「CSP の配線」にも手を触れずに済む。
  （`WKUserScript` で `window.__native` を注入する形も動くが、CSP との
  関係が版によって変わりうる面倒を抱え込む。避ける。）
- ネイティブ側が知るのは「文字列の配列 in / 文字列の配列 out」だけ。
  アプリの都合が漏れないので、殻を作り直しても壊れない。

### 5.3 Web 側の受け口

`app/lib/native.ts` を1本足して、能力の検出だけを閉じ込める。

```ts
export function nativeTranslate(): ((texts: string[], target: string) => Promise<string[]>) | null
```

Safari で開いたときは `null` を返し、翻訳ボタンを出さない。**Web 版が
片肺で壊れないことが④の条件**なので、ここは分岐ではなく「無ければ出ない」で
書く。差分は数十行に収まる。

### 5.4 何を翻訳の単位にするか

本文を丸ごと投げてはいけない。Markdown が壊れる（コードブロックが訳され、
数式の `\frac` が別物になる）。

既にある `app/lib/markdown-blocks.ts` の塊分割が、そのまま使える。塊のうち
コードブロック・数式・URL を除いた地の文だけを取り出して配列で投げ、
戻ってきた順に埋め戻す。`TranslationSession` は複数まとめて投げられるので、
往復は塊の数に比例せず1回で済む。

訳の置き場は「原文と並べてトグル」が素直。**D1 には保存しない**方向で考える
——オンデバイス翻訳の結果は端末と OS の版で変わりうるので、保存すると
「同じ会話なのに端末で違う」が起きる。

### 5.5 ついでに殻から渡せて嬉しいもの

| | なぜ Web だけでは無理か |
|---|---|
| 触覚（Haptics） | iOS Safari に Vibration API が無い |
| 端からのスワイプで戻る | Web の history では感触が出せない |
| 生成完了のローカル通知 | 前面にいないと気づけない。ただし完了時刻が読めないので設計が要る |
| 写真ピッカー・共有 | `input[type=file]` と Web Share で足りている。**急がない** |

③はここで稼ぐ。全部いっぺんにやらず、翻訳が動いてから足す。

### 5.6 段取り

| | やること | 目安 |
|---|---|---|
| Phase 0 | 空の Xcode プロジェクト + WKWebView。Access のログインが通ることの確認 | 半日 |
| Phase 1 | 翻訳ブリッジ（殻側 + `app/lib/native.ts` + 翻訳ボタン） | 1〜2日 |
| Phase 2 | 触覚・スワイプ戻る・バウンスの調整 | 半日 |
| Phase 3 | 不満の出た画面だけ C（ネイティブのクローム）へ | 都度 |

Phase 1 まで来れば①は満たされる。Phase 2 以降は「やらなくてもよい」状態で
止められる——これが B を推す一番の理由でもある。

## 6. 先に潰しておく穴

### 6.1 Cloudflare Access のログインが WebView で通るか【要確認・最重要】

アプリは Access の後ろにいる（要件 §2.2）。WKWebView は Safari と Cookie を
共有しないので、**WebView の中で1回ログインする**ことになる。
`WKWebsiteDataStore.default()` を使えば Cookie は再起動をまたいで残り、
セッションは1ヶ月なので実用上は十分。

危ないのは IdP の選択で、**Google の IdP は埋め込み WebView からのログインを
拒む**ことがある（"This browser or app may not be secure"）。
対策は上から順に:

1. Access のポリシーを**メール OTP** にする。WebView 内で完結する。
2. Access の**サービストークン**（`CF-Access-Client-Id` / `-Secret`）で
   `URLSession` から1回叩き、返ってきた `CF_Authorization` を
   `WKWebsiteDataStore` へ移す。自分の端末に置く秘密なので、単独利用なら
   釣り合う。**要確認**: サービストークン認証で Cookie が返るか。

Phase 0 でここが通らなければ、その先は全部無駄になる。**最初に確かめる。**

### 6.2 端末ローカルの設定が、週に1度消えないか【要確認】

無料署名は7日で切れる（§3）。WKWebView の localStorage はアプリのコンテナに
入るので、**アプリを消して入れ直すと消える**。消えるのは:

- テーマ・アクセント色・文字サイズ（`app/lib/settings.ts` `theme.ts`）
- よく使うモデルの記録（`app/lib/recent-models.ts`。半減期2週間で貯めているので、
  毎週消えると「よく使う」が永久に育たない）
- 書きかけの下書きと添付（`Chat.tsx`）

Xcode から上書きで再インストールする限りコンテナは残る見込みだが、**確かめる**。
消えるなら手当てが要る:

- 殻の側で localStorage を `UserDefaults` へ退避・復元する（殻が厚くなる）
- よく使うモデルと表示設定を D1 へ寄せる（要件 §3.1・§3.7 は「端末ごとの好み
  だから localStorage」と決めているので、**要件の変更**になる）

### 6.3 iOS 18 未満なら①が成立しない

`TranslationSession` は iOS 18 から。端末の版を先に確かめる。

### 6.4 採用したら要件も直す

このリポジトリの決まり（CLAUDE.md）に従い、実装に入る時点で
`docs/requirements.md` の次を直す。**いまは何も決まっていないので触っていない。**

- §1.2 利用環境（端末に「iPhone（ネイティブアプリ）」を足す）
- §3.8 モバイル対応（殻の存在と、殻が持つ機能）
- §6 スコープ外（ネイティブアプリを外す）
- 翻訳機能そのものの節（§3.3 のどこか）

## 7. 評価のまとめ

- ①が無ければ **A（PWA のまま）が最良**。ネイティブ化は①を買うための出費で、
  それ以外の条件はどれもネイティブ化を求めていない。
- ②はどの案でも同額（無料署名 + 週1の再インストール）。**案の優劣を決めない**。
  効いてくるのは CI で、それは「ネイティブを小さく保つ」に帰着する。
- ③はフルネイティブ（E）が最高だが、**数式と図のために結局 WebView が残る**ので
  満点にならない。殻（B）でも、触覚・スワイプ・シートは取れる。
- ④は E・F で決定的に壊れる。16,887行の表示層と 9,380行のテストが二重になる。
- したがって **B を採り、不満の出た画面だけ C へ寄せる**。この順序なら、
  いつでも止められて、止めた地点が常に「動く状態」になる。
